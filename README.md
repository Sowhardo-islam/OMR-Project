# PAPERSTORE OMR

![Python](https://img.shields.io/badge/Python-3.x-blue?logo=python&logoColor=white)

**PAPERSTORE OMR** is a custom paper-based data storage prototype. It converts UTF-8 text into a dense black-and-white grid, saves that grid as an image, and later reconstructs the original text from the image using OpenCV-based cell sampling.

> **Important:** This project is **not a QR-code implementation**. It uses a custom fixed-grid OMR-like format with its own packet structure, timing cells, alignment markers, finder markers, and CRC-32 integrity check.

## Preview

The repository includes an encoded example image generated by the project:

![Encoded PAPERSTORE OMR example](output/code%2817%29.png)

The example is an A4 page generated with a **17-pixel cell size**.

---

## Features

- Store UTF-8 text in a printable black-and-white grid
- Encode `.txt` files into PNG images
- Decode encoded images back into text files
- Deterministic row-major bit traversal
- Fixed timing row and timing column
- Periodic alignment dots
- Four visual finder markers
- CRC-32 integrity verification
- A4, A5, and LETTER page presets
- Adjustable cell size
- OpenCV adaptive thresholding during decoding
- Simple command-line interface
- Windows executable included in the original distribution

```text
    │

                DECODE

    │

    │

    │
    ▼

    │

    │

    │
```

The current decoder uses the known image geometry and the **cell size supplied by the user**. It does not yet perform automatic page detection, perspective correction, rotation detection, or cell-size detection.

## Paper Sizes

The source defines the following pixel dimensions:

```python
PAPER_SIZES = {
    "A4": (2480, 3508),
    "A5": (1748, 2480),
    "LETTER": (2550, 3300)
}
```

The default margin is:

```python
DEFAULT_MARGIN = 160
```

The grid dimensions are derived from the paper dimensions, margin, and selected cell size:

```text
grid_width  = (paper_width  - 2 × margin) // cell_size
grid_height = (paper_height - 2 × margin) // cell_size
```

## Data Packet Format

Before the payload is drawn into the grid, the encoder builds a packet.

Conceptually:

```text
┌──────────────────────┬────────────────────┬─────────────────┐
│ Header length (4 B)  │ JSON metadata      │ UTF-8 payload   │
└──────────────────────┴────────────────────┴─────────────────┘
```

### 1. Header Length

The first four bytes contain the JSON header length as a big-endian unsigned integer:

```python
len(header).to_bytes(4, "big")
```

### 2. JSON Metadata

The metadata contains the payload length and CRC-32:

```json
{
  "size": 1234,
  "crc": 123456789
}
```

The CRC is generated with:

```python
zlib.crc32(raw)
```

### 3. UTF-8 Payload

The input text is converted to bytes with:

```python
raw = text.encode("utf-8")
```

This allows normal ASCII as well as Unicode text, provided the complete packet fits in the available grid.

---

## Bit Encoding

Each byte is converted into eight bits.

Example:

```text
0x41 → 01000001
```

The resulting bit stream is written into available grid cells in **row-major order**:

```text
left → right
next row ↓
```

The representation is simple:

```text
0 = white cell
1 = black cell
```

The decoder reads the same cells in the same order and reconstructs the original bytes.

---

## Grid Layout

Not every cell stores data. Several locations are reserved for visual structure.

### Reserved Timing Row

```python
y == 0
```

The complete first grid row is reserved.

### Reserved Timing Column

```python
x == 0
```

The complete first grid column is reserved.

### Alignment Cells

A cell is also reserved when:

```python
x % 20 == 0 and y % 20 == 0
```

These locations are used for alignment dots.

Therefore:

```text
raw grid cells != actual data cells
```

Only non-reserved cells can store payload bits.

---

## Timing Pattern

Alternating black timing blocks are placed along the top and left edges.

The source generates them using alternating positions such as:

```python
i % 2 == 0
```

These patterns visually indicate the intended grid spacing.

The current decoder does **not** automatically detect these timing patterns. They are structural and visual guides in the current prototype.

---

## Alignment Dots

Alignment markers are placed every:

```python
ALIGN_EVERY = 20
```

A marker is placed when both grid coordinates are multiples of 20.

These markers are currently skipped as reserved cells. The decoder does not yet use them as computer-vision landmarks for automatic geometric correction.

---

## Finder Markers

Four visual markers are placed around the page:

- Top-left square
- Top-right square
- Bottom-left square
- Bottom-right circle

They are intended to make page location and orientation easier to identify visually and to provide landmarks for a future computer-vision decoder.

The current decoder does **not** use the finder markers for automatic perspective correction or rotation detection.

## Decoder Pipeline

The decoder follows these stages.

### 1. Load the image

OpenCV loads the selected file:

```python
cv2.imread(path)
```

### 2. Convert to grayscale

```python
gray = cv2.cvtColor(img, cv2.COLOR_BGR2GRAY)
```

### 3. Apply adaptive thresholding

The current implementation uses Gaussian adaptive thresholding:

```python
cv2.adaptiveThreshold(
    gray,
    255,
    cv2.ADAPTIVE_THRESH_GAUSSIAN_C,
    cv2.THRESH_BINARY_INV,
    31,
    5
)
```

### 4. Reconstruct the grid

The decoder uses:

- input image dimensions
- fixed margin of `160` pixels
- user-provided cell size

### 5. Sample cells

Only the central part of each cell is sampled. The sample size is approximately 30% of the cell size:

```python
s = int(cell * 0.30)
```

The decoder determines whether the cell represents `0` or `1` from the amount of detected black pixels.

A cell is treated as `1` when the sampled area exceeds the current black-pixel threshold of approximately 60%.

### 6. Rebuild bytes

The bit stream is reconstructed in groups of eight.

### 7. Parse and validate the packet

The JSON header is parsed and the payload CRC-32 is recalculated.

### 8. Recover the text

After successful validation, the UTF-8 payload is written to:

```text
output/recovered.txt
```

## Cell Size

Cell size is one of the most important parameters in the current design.

The source comments recommend roughly:

```text
16–20 pixels
```

The supplied `info.txt` mentions `8` as a lower setting and `17` as a recommended value. The current CLI does not enforce these limits.

### Smaller Cells

- More storage capacity
- Denser pages
- Greater sensitivity to blur
- Greater sensitivity to printing/scanning errors
- Less tolerance for resizing and distortion

### Larger Cells

- Less storage capacity
- Easier visual separation
- Better resistance to blur and resampling
- Generally easier to scan reliably

For the included example, **17 pixels** is the most useful reference configuration.

## Capacity

Each non-reserved cell stores one bit:

```text
data_bits  = number of non-reserved cells
data_bytes = floor(data_bits / 8)
```

The packet header consumes additional space, so the actual maximum text payload is slightly smaller than the raw capacity.

### Approximate Raw Capacity

The following values are derived from the current `main.py` grid calculations and exclude packet overhead:

| Paper | Cell Size | Grid | Approx. Raw Capacity |
|---|---:|---:|---:|
| A4 | 16 | 135 × 199 | ~3.23 KiB |
| A4 | 17 | 127 × 187 | ~2.85 KiB |
| A4 | 20 | 108 × 159 | ~2.06 KiB |
| A5 | 16 | 89 × 135 | ~1.44 KiB |
| A5 | 17 | 84 × 127 | ~1.27 KiB |
| A5 | 20 | 71 × 108 | ~0.91 KiB |
| LETTER | 16 | 139 × 186 | ~3.11 KiB |
| LETTER | 17 | 131 × 175 | ~2.75 KiB |
| LETTER | 20 | 111 × 149 | ~1.98 KiB |

> These numbers describe the current software geometry. They are not a promise of real-world printable storage capacity.

### Capacity Warning

`info.txt` contains a historical example claiming approximately `14.71725 KB ± 0.00005 KB` at cell size `8`. That value does **not exactly match** the capacity produced by the current `main.py` calculations. For the current project, the source code should be treated as authoritative.

The encoder also does not currently perform a proper pre-encode overflow check. A production version should calculate packet size and reject inputs that cannot fit.

A reliable test workflow is:

```text

2. Run python main.py
3. Select Encode Text File
4. Select A4
5. Use cell size 17
6. Generate the PNG
```

Testing the original PNG first is important because it separates software bugs from printing and camera problems. Debugging all variables simultaneously is a fine human tradition, but a poor engineering strategy.

## Limitations

This project is currently a **fixed-grid prototype**, not a production-grade document scanner.

### No automatic perspective correction

The decoder expects the page to remain close to the original geometry.

### No automatic rotation detection

Finder markers are not currently analyzed to determine orientation.

### No automatic cell-size detection

The user must provide the cell size during decoding.

### No automatic page detection

The decoder assumes the supplied image already represents the encoded page.

### Fixed margin

The current implementation relies on:

```text
margin = 160 pixels
```

Changing geometry constants without keeping encoder and decoder in sync can make old pages unreadable.

### No error correction

CRC-32 detects many corruptions but does not repair damaged data.

### No Reed-Solomon in the current implementation

Although `reedsolo` is present in `requirements.txt`, the supplied source does not use it.

### Payload overflow is not explicitly rejected

The current encoder should be improved to detect over-capacity payloads before creating the image.

### Limited image tolerance

Blur, scaling, JPEG compression, rotation, cropping, perspective distortion, shadows, glare, and printing defects can all cause bit errors.

---

## Security

The format provides **integrity checking**, not security.

CRC-32 can detect accidental corruption, but the project does not provide:

- Encryption
- Authentication
- Password protection
- Confidentiality
- Cryptographic tamper protection

Anyone who can read the encoded page and understands the format can recover the stored text.

Treat PAPERSTORE OMR as **encoded storage, not secure storage**.

---

## Design Philosophy

The project intentionally uses a known master grid instead of relying on full computer-vision synchronization during decoding.

This provides:

- Deterministic coordinates
- Simple encoding
- Simple decoding
- Predictable traversal
- Low algorithmic complexity
- Easy image generation with Pillow
- Easy cell sampling with OpenCV

The trade-off is reduced tolerance to physical distortion.

In other words, the prototype keeps the software simple by asking the paper to behave itself. Paper, being paper, is not always cooperative.

## Future Improvements

The existing packet/grid design can be extended without replacing the whole project.

### Automatic Page Detection

Use the finder markers to locate the page in a camera frame.

### Perspective Correction

Detect page corners and apply a homography before sampling the cells.

### Rotation Detection

Use asymmetric finder markers or marker geometry to determine orientation automatically.

### Automatic Cell-Size Detection

Estimate grid spacing from timing patterns and alignment dots instead of asking the user.

### Error-Correction Coding

Add Reed-Solomon or another forward-error-correction layer so damaged or missing cells can be reconstructed.

### Capacity Validation

Calculate the packet size before drawing and show the maximum supported payload size.

### Multi-Page Storage

Large files could be split across numbered pages containing metadata such as:

```text
format version
project ID
page number
page count
payload length
CRC
```

### Binary File Support

The packet is already byte-oriented internally, so the system could be extended to store arbitrary binary files instead of text only.

### Compression

Compress the payload before encoding to increase effective text capacity.

### Better Print Layout

The development grid could eventually be replaced with a cleaner production layout while keeping the same logical cell format.

### Format Versioning

Packet metadata could include a format version, for example:

```json
{
  "version": 1,
  "size": 1234,
  "crc": 123456789
}
```

This would make future format changes safer.

## Compatibility

An encoded page depends on the geometry and packet rules used by the encoder.

At minimum, the following must remain compatible between encoder and decoder:

```text
Paper dimensions
Margin
Cell size
Reserved-cell rules
Traversal order
Packet format
```

Changing constants such as:

```python
DEFAULT_MARGIN
ALIGN_EVERY
PAPER_SIZES
```

can make previously generated pages incompatible with a newer decoder unless backward compatibility is implemented.
